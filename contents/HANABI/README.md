# HANABI

3次元の花火シミュレーションについて、設計方針を検証するためのモックアップ。
見た目を作り込むのが目的ではなく、**方針が成立するかを実際に測って確かめる**ためのもの。

```
py .claude/nocache_server.py 8103     # または .claude/launch.json の "hanabi"
```

`py -m http.server` ではなく no-store を付けるサーバーを使う。
素の http.server は Last-Modified しか返さず、JS を書き換えてもブラウザが
古い ES モジュールを掴んだままになる。実際それで一度、
「renderer.js は新しいのに camera.js だけ古い」という状態にはまった。
それでも古いままなら Ctrl+F5。

操作は縦ドラッグ（とホイール）で距離、Space で打ち上げ。周回はしない。
コンソールから `window.HANABI` で中身を直接触れる。

画面の両端にタブがある。**左 `SCENE` が世界の設定**（シーン・背景・描画）で、
一度決めたらあまり触らない。**右 `RECIPE` が花火そのもの**で、こちらは常に触る。
広い画面なら両方同時に開ける（560px 以下では排他）。

玉の中身は **レシピ**（[recipes.json](recipes.json)）で組み替える。
右パネルでブロックを押すと**その場で開いて中身が出る**（アコーディオン）。
開くのは常に 1 つだけなので、閉じたブロックは 1 行で済み、
入れ子の構造を見失わずに編集できる。分裂の行は親を畳んでいても残るので、
開かないと子の存在が分からない状態にはならない。

原本（recipes.json 読み込み時／設定ファイル読み込み時の状態）と違うところには
`•` が出る。ドロップダウンの項目名にも、樹のブロック見出しにも。
`↺ RESET` でその原本へ戻る。

レシピは名前をその場で書き換えられ、`◉ ON` / `○ OFF` で
**MIX と AUTO LAUNCH の抽選から外せる**（OFF でも選んで編集・`▶ LAUNCH`・Space は効く）。
初期状態は全部 ON。無効化したものだけ recipes.json に `"on": false` が残る。

`⧉ JSON` で現在のレシピ 1 つを、左タブ `CONFIG` の `⭳ SAVE` で
**全設定**（SCENE / SKY / RENDER の全値＋レシピ一覧・名前・ON/OFF・MIX）を
`hanabi-config.json` に書き出す。`⭱ LOAD` で丸ごと差し替え。
読み込んだレシピが新しい原本になるので、直後は `•` が消える。
コンソールからは `HANABI.exportConfig()` / `HANABI.loadConfig(obj)`。

## 設計の核

線形抵抗 `dv/dt = G - (v - w)/tau` は閉じた解を持つ。

```
v_T  = tau*G + w                                  終端速度（風は足すだけ）
p(t) = p0 + v_T*t + tau*(v0 - v_T)*(1 - e^(-t/tau))
v(t) = v_T + (v0 - v_T)*e^(-t/tau)                速度も閉じている
```

これを頂点シェーダで直接評価している（[js/shaders.js](js/shaders.js)）。
前フレームの状態を参照しないので、

- 星の属性 VBO は**起動時に一度書くだけ**。発火時ですら書き込みが発生しない
- 毎フレーム更新する uniform は玉ごとの `uAge` ひとつ
- フレームレート非依存。30fps に落としても軌道は数学的に同一
- タブ復帰で巨大な dt が来ても、新しい t で評価するだけで正しい

調整するのは `RADIUS` / `FALL SPEED` / `LIFE` の3つだけで、
`tau = FALL SPEED / g`、`|v0| = RADIUS / tau` を内部で逆算する。
tau や抵抗係数を直接触っても見た目の予想が立たないため。

## レシピ

玉の中身は [recipes.json](recipes.json) にある。エンジンとは直交していて、
物理には一切触れずに組み替えられる。

```json
{
  "name": "SENRIN 2C",
  "shells": [
    {
      "type": "peony", "size": "large",
      "colors": ["magenta"],
      "split": {
        "at": 0.40, "type": "peony", "size": "small",
        "colors": ["cyan", "green"], "colorLate": "silver", "inherit": 0.3
      }
    }
  ]
}
```

| キー | 効果 |
|---|---|
| `shells[]` | 同時発射。原点と昇りを共有するので1発に見える。`delay` で少しずらせる |
| `type` | 形の性格（牡丹／菊／柳／冠菊／環）。抵抗・ばらつき・扁平を決める |
| `size` | スケール（L / M / S / XS）。`type` の寸法に掛かる |
| `colors[]` | 星ごとの色分け。最大4色 |
| `colorLate` | 時間経過でこの色へ寄る（窓は COLOR SHIFT で全玉共通） |
| `split` | 分裂。`at` は親の寿命に対する割合、`inherit` は親の速度の引き継ぎ量 |

`type` と `size` を分けてあるのは、「大サイズ色A と 中サイズ色B の重ね」のような
**同じ型の大小を重ねる**組み方が花火の基本形だから。
`shells` に2つ並べて `size` だけ変えれば作れる。

`colorLate` を付けると `lateFrom` / `lateTo`（既定 0.30 / 0.75）で
変化の窓を指定できる。**その段の寿命に対する割合**なので、
寿命を変えても相対位置は保たれるし、分裂する玉では親と子で別々に持てる。

省略した項目は [js/recipes.js](js/recipes.js) の正規化が埋める。
未知の色名・4色超過・深すぎる入れ子はここで落とすので、
シェーダ側で範囲外を引くことはない。

## 固定した値

検証が終わって答えが出たものはスライダーから外した。
残しておくと毎回いじって迷うだけで、決まったあとは動かす理由がない。
触りたくなったら `window.HANABI.params` から書き換えられる。

| | 値 | 置き場 |
|---|---|---|
| 重力 | 9.8 m/s² | [js/presets.js](js/presets.js) |
| 風 | 0 m/s | 同上（線形抵抗の副産物でタダなので式には残してある） |
| 背景の利得 | 2.0 | [js/sky.js](js/sky.js) |
| 星の格子 / 密度 / 大きさ | 600 / 5% / 0.15 | 同上 |
| 地面 | 黒 | 同上 |
| 芯の点サイズ上限 | 1px | [js/renderer.js](js/renderer.js) |
| DPR | 1 | 同上（PIXEL SIZE の整数倍を保証するため） |

段が決まっているものはスライダーではなくボタン列にした
（`HAZE` の HIGH/MID/MIN/OFF、`TREELINE` の ON/OFF、`PIXEL SIZE` の x1/x2/x3）。
スライダーだと「HIGH と MID の間」のような意味のない値に止められてしまう。

## 検証結果

### 1. 線形抵抗＋ばらつきで「垂れ下がり」は出るか → 条件付きで出る

線形抵抗だけでは**球はまったく歪まない**。全粒子で tau が同じなら

```
p_i(t) - 重心(t) = tau * v0_i * (1 - e^(-t/tau))
```

が v0 にスカラーを掛けただけなので、分布は最後まで真球のまま平行移動する。
垂れ下がりは重心が沈むぶんだけで、形は崩れない。

`DRAG SPREAD`（tau のばらつき）を入れると縦方向に尾を引くが、
**これが効くのは `LIFE >> tau` のときだけ**だった。tau に対する落下量の感度は

```
d(落下)/d(tau) ≈ -g*t + 2*g*tau*(1 - e^(-t/tau))
```

で、`t/tau` が 1 前後だと第1項と第2項がほぼ打ち消し合う。
柳のプリセット（tau 3.47 / life 5.5、`LIFE/tau = 1.6`）では実際ほとんど尾が出ず、
球のまま沈むだけだった。

**結論：** 柳らしさは星の分布の歪みではなく、**落下する星が引く長い光跡**でできている。
形ではなく尾で作るべきものだった。TRAIL を 0.18s → 0.6s にしたところで柳に見えるようになった。

### 2. D/R はどこから平面に見えるか → 3前後を保つ必要がある

視距離 D と炸裂半径 R の比だけで立体感が決まる。近／遠の見かけ比は `(D+R)/(D-R)`。

| D/R | 近/遠 |
|---|---|
| 2.8（尺玉の実物） | 2.0 |
| 5 | 1.5 |
| 10 | 1.22 |
| 20 | 1.11 ≒ 平面 |

**最初この既定値を間違えた。** プリセットを小玉スケール（R=25m）のまま
尺玉の高度（330m）と観覧距離（430m）に置いたので D/R が 21.7 になり、
まさに「平面に見える」領域に入っていた。
プリセットを尺玉スケール（R=160m）に直して D/R 3.14 に揃えてある。

D/R と FOV は両方がフレーミングを決めるが、**立体感は D/R だけ**が決める。
`D/R=3, fov=37` と `D/R=20, fov=5.7` は同じ大きさに写り、後者は平面。
調整は「D/R を先に固定 → FOV でフレーミング」の順で行う。

HUD に D/R と近/遠比を常時出してあるのはこのため。

#### カメラは 2 変数だけで決まる

発射地点は原点固定、周回はしない。カメラは水平に `D` 離れた目線の高さ（1.6m）に立ち、
常に開花点 `(0, H, 0)` を向く。

```
θ = atan((H - 1.6) / D)
```

`DISTANCE` と `ALTITUDE` の 2 つだけで位置も向きも決まる。実測値：

| D(水平) | θ | 斜距離 | D/R | 近/遠 | 地平線 |
|---|---|---|---|---|---|
| 30 m | 84.8° | 330 | 2.06 | 2.88 | — |
| 120 | 69.9° | 350 | 2.19 | 2.69 | — |
| 380 | 40.8° | 502 | 3.14 | 1.94 | — |
| 707 | 24.9° | 780 | 4.87 | 1.52 | 見える |
| 1500 | 12.3° | 1536 | 9.60 | 1.23 | 見える |
| 2500 | 7.5° | 2521 | 15.76 | 1.14 | 見える |

**D/R は水平距離ではなく斜距離 √(D² + H²) で決まる。**
だから `D → 0` にしても斜距離は `H` で下げ止まり、**真下から見上げても
花火は一定以上大きくならない**。H=330 / R=160 なら D/R = 2.05 が下限で、
実際に最小距離 20m まで詰めても 2.06 だった。真下に立っても高度ぶんの
距離は残るので、これは物理的に正しい。

副作用として、**距離スライダーが実質「立体感スライダー」になった**。
D を 20→3000 で振ると D/R が 2.06→15.8 まで動く。上の「立体感は D/R だけが決める」が
スライダー 1 本に落ちたので、操作としてはむしろ分かりやすくなった。
対数で動かしているのは、効くのが絶対距離ではなく比だから。

**地平線が入るのは θ < FOV/2 のときだけ**で、FOV 50 度なら `D > 2.14 × H`。
H=330 で 704m。樹立が見えるのはそれより引いたときに限られる。

### 3. 奥行きが読める最低の内部解像度 → 1/2〜1/3

### 3. 奥行きが読める最低の内部解像度 → 1/2〜1/3

`INTERNAL RES` を下げると塗る量が `1/n^2` になるが、点サイズが 1〜4px に潰れて
遠近のサイズ差（＝主要な奥行き手がかり）が失われる。両者の折り合いは 1/2〜1/3。

性能の実測（1920x1080 / 10発 × 2000星 / readPixels 同期込み）：

| 内部解像度 | ms/frame |
|---|---|
| 1/1 | 2.75 |
| 1/2 | 0.79 |
| 1/3 | 0.78 |
| 1/4 | 0.79 |

**1/2 より下げても速くならない。** 1/2 以下は同期コストに埋もれていて、
GPU 側の実仕事はすでに無視できる。つまり下げる意味は「見た目」だけで、
奥行きを失うぶん損になる。

星の数を 2000 → 4000 に倍増しても 0.78 → 0.86ms（+10%）で、
**頂点律速ではない**ことも確認できた。40,000 星でもコストはほぼ変わらない。

なお `INTERNAL RES` は `PIXEL SIZE`（x1 / x2 / x3）に置き換えた。
中身は同じ（1/n で描いて n 倍に伸ばす）だが、
「拡大率」として見せたほうが何が起きるか読める。

#### 芯の点サイズは 1px に固定した

`MAX PX` を消して常に 1px にしてある。これは上の「遠近のサイズ差が
主要な奥行き手がかり」という実測に**正面から反する選択**なので、
何と引き換えたかを書いておく。

丸め補償 `vComp = (sWant/sUse)²` が残るので、サイズを切り詰めたぶんは
輝度に回る。つまり遠近の手がかりが「大きさの差」から「明るさの差」へ移る。
サイズ差ほど強い手がかりではないが、消えるわけではない。
引き換えに、星が必ず画面グリッドの 1 マスに乗るのでドット絵として揃う。

見た目を取って奥行きを一段譲った、と理解しておくのが正しい。

### 4. 種類の描き分け → 初速・抵抗・寿命だけで足りる

牡丹 / 菊 / 柳 / クラックル / 環はすべて同じシェーダで、パラメータ差だけで出ている。
環（`FLATTEN`）は方向ベクトルを平面に潰すだけで、シェーダは1行も変えていない。

ただし環は**向きをカメラ側に寄せる必要があった**。完全ランダムな向きにすると
真横を向いた環がただの光の棒になる。実物の型物も観客側へ開くよう仕込まれている。

### 5. 分裂（千輪／分砲）を解析解のまま書けるか → 書ける

**速度まで閉じている**のが効いた。分裂時刻 `ts` での状態 `(p(ts), v(ts))` を
そのまま第2区間の初期値にすれば、分裂は「もう一区間の解析評価」になる。

```
ps  = p(ts)
vs  = v_T + (v0 - v_T)*e^(-ts/tau)
v0' = vs*inherit + dir2*speed2
p(t>ts) = ps + v_T2*(t-ts) + tau2*(v0' - v_T2)*(1 - e^(-(t-ts)/tau2))
```

`t = ts` で第2区間は `ps + 0` になるので、**位置の連続性は構成上そのまま成り立つ**。
実測した分裂点のギャップは `8.6e-5 m`（有限差分 eps=1e-6 のぶんだけで、実質ゼロ）。
星が飛ばない。速度のほうは意図的に不連続で、それが分裂そのものになる。

積分もフィードバックも要らないので、**1玉 = 1 draw call のまま**で、
発火時の VBO 書き込みもやはりゼロ。第2段の方向 `aDir2` も起動時に一度書くだけ。

形の変化も測れた（発光画素の広がりと、中心から 0.8R より外／0.5R より内の比）：

| | 大きさ | 縁/中心 |
|---|---|---|
| 牡丹 age 1.2 | 272px | 1.38 |
| 千輪 age 0.85（分裂前） | 209px | 1.31 |
| 千輪 age 1.70（分裂後） | 311px | 1.06 |
| 環 age 1.2 | 323px | 26.9 |

分裂前は薄い球殻（縁が明るい）、分裂後は広がって殻が厚い雲になる。
親の殻の各点から子が四方に開くので当然こうなるべきで、潰れていない。

**制約：子の粒子数は親と同数**になる。各粒子が1本の子へ *continue* する形なので、
実物の千輪のような「1粒 → 20粒」の fan-out ではない。分裂時に方向・速度・色を
全部振り直すので二段咲きには見えるが、粒子密度は増えない。
密度が欲しければ STARS を上げる（下の実測どおり安い）。

### 6. 背景を足すと何が犠牲になるか → 黒レベルぶんだけ、しかも頭打ち

星空・地面・樹立を足した（[js/sky.js](js/sky.js)）。パネルの SKY で
`NONE` / `STARS`（手続き）/ `HDRI`（等角図法テクスチャ）を切り替えられる。

**トレイルバッファに描いてはいけない。** あれは前フレームを減衰させて足し込む
フィードバックループなので、静止した空でも毎フレーム「減衰して再加算」され、
蓄積利得 `1/(1-fade)` 倍まで飽和する。しかも fade は TRAIL スライダーで動くから、
**尾の長さを変えた瞬間に空の明るさが変わる**。上の「トレイル長と露出は独立ではない」と
まったく同じ罠で、今度は背景が巻き込まれる。

なので空は独立したバッファに描き、present で `tonemap(sky*skyBright + trail*exposure)`
として足している。空も trail と同じ内部解像度に描くので、同じ NEAREST 整数倍で
引き伸ばされて**完全に同じピクセルグリッドに乗る**（キャンバス解像度で描くと、
カリカリの花火となめらかな背景が同居して事故る）。

コストは **0.11ms**（花火なしで 0.92 → 1.03ms）。花火を足すと測定ノイズに埋もれる。

#### 花火の見え方はどれだけ損をするか

同じ玉を使い回して（`SCATTER 0`）、空だけの絵と空＋花火の絵の差を取り、
「花火がまだ見分けられる画素」を数えた。暗い尾は差 2〜40、芯は 40 以上。

柳（尾が長く暗い / 地平線が画角外の構図）：

| SKY LEVEL | 尾が残る | 芯が残る |
|---|---|---|
| 0（真っ黒） | 100% | 100% |
| 0.35 | 89.8% | 78% |
| 0.50 | 89.6% | 78% |
| 1.00 | 89.2% | 78% |
| 2.00 | 89.0% | 77.9% |

牡丹は尾 84.9% → 84.6%、芯は 94.2% でほぼ横ばい。

**空を点けた瞬間に1割ほど失い、そこから 6 倍明るくしてもほとんど変わらない。**
黒レベルが 0 から離れた時点で、8bit で 2〜3 階調しかなかった尾が差として
出なくなるためで、それより明るくしても残っている画素はもともと明るい。
だから `SKY LEVEL` は「上げすぎ厳禁」ではなく「点けるかどうか」の判断になる。

#### 地面と樹立は花火の見え方に影響しない

`GROUND` を 0 から 0.2 まで振っても、`TREELINE` を切っても、
花火側の数値がまったく動かなかった。理由は幾何で、

| | 仰角 |
|---|---|
| 柳の最下部の星（219m まで落ちる） | 29.8° |
| 樹立の頂点 | 4.7° |

**画面上で重ならない。** 尺玉は 330m で開いて 219m までしか落ちないので、
地平線付近には最初から来ない。背景を足すのはタダ、という結論になる。

#### 既定の画角に地平線は入らない（これは正しい）

視線が 40.8° 上を向いていて縦半画角が 25° なので、下端が +15.8°。
地面も樹立も画面の外にある。380m から尺玉を見上げれば実際そうなるので
構図としては正しく、`DISTANCE` を 704m より引くと入ってくる。

ただし既定の距離では**炸裂全体と地平線を同時には入れられない**。
玉の角半径が 22° あるので、50° の画角に両方は乗らない。
実際の花火大会で広角レンズなしに両方撮れないのと同じ理屈。

なお地面は黒に固定した。夜の地面に見せるだけなら黒で足りるうえ、
樹立のシルエットは空を切り取ることで読めるので、地面側の明るさは要らない。

### 7. 多色化のコスト → ゼロ

星ごとの色分けは「どの色を引くか」を静的属性 `aMeta.x` の抽選で決めている。
パレットは `uniform vec3[4]` で渡すだけなので、**何色使っても draw call も帯域も増えない**。
経時変化（色A→色B）は頂点シェーダ内の `mix` 1回で、これもコストが乗らない。

性能の実測（内部解像度 1/3・readPixels 同期込み）：

| | ms/frame |
|---|---|
| 1発・分裂なし（1500星） | 1.11 |
| 1発・分裂あり（1500星） | 1.50 |
| 15発（22,500星） | 2.00 |
| 15発（60,000星） | 2.56 |

分裂ありが 35% 重いのは、頂点シェーダの分岐が SIMD で両方の枝を通るため。
それでも 1.5ms で、星を 2.7倍（22,500 → 60,000）にしても +28% しか増えない。
**頂点律速ではない**という結論は分裂を足しても変わらなかった。

## 実装上つまずいた点

**点サイズは整数に丸める必要がある。** 小数のままだとカメラ移動でサブピクセル明滅が出る。
丸めたぶんは面積比 `(sWant/sUse)^2` で輝度補償しないと、サイズが切り替わる距離に
輝度の段差が輪になって現れる。

**加算輝度は内部解像度に依存する。** ピクセル1個が受け持つ立体角が解像度の2乗で変わるので、
補正しないと解像度を変えた瞬間に露出がまるごとずれる。

**トレイル長と露出は独立ではない。** フィードバックバッファの蓄積利得は `1/(1-fade)` なので、
尾を伸ばすとそのぶん明るくなる。補正前は TRAIL を 0.86 → 0.975 にした瞬間に真っ白に飽和した。
現在は時定数で持って `(1-fade)` で補正しているので、TRAIL を動かしても露出が変わらない。

**トレイルはフレームレート依存にしてはいけない。** 「1フレームあたりの係数」で持つと
30fps と 60fps で尾の長さが変わる。時定数にして `fade = exp(-dt/T)` で計算している。

**露出を上げすぎると球の縁の明るさが消える。** 球面一様分布を加算合成すると、
縁は接線方向に殻を長く貫くので投影密度が `1/sqrt(1-b^2/R^2)` で発散し、
勝手にリムが明るくなる（＝球に見える最大の手がかり）。
最初これを白飛びで潰していた。露出を下げたら縁/中心比が 1.31、環では 2.2 まで出るようになった。

## この設計の弱点（未解決）

**トレイルがスクリーン空間なので、カメラを速く動かすと尾の向きが嘘になる。**
周回を廃したので横に振られることはなくなったが、距離を素早く変えると
今度は放射状に引きずられる。ワールド空間の運動とは無関係な方向。

**トレイル長が全玉で共通。** 牡丹は 0.18s、柳は 0.6s が似合うのに、
フィードバックバッファは画面全体に一律にかかるので玉ごとに変えられない。

どちらも `p(t)` と `p(t-dt)` を結ぶ instanced quad（解析的な軌跡線分）に
置き換えれば同時に解決する。`v(t)` も閉じた式で持っているので線分は厳密に引ける。
頂点数は4倍になるが、上の実測どおり頂点律速ではないので問題にならないはず。

**色の補間が線形なので、遷移の途中がグレーを通る。**
`mix(blue, gold, t)` は色相環ではなく RGB 直線を通るので、
青 `(0.28,0.55,1.0)` → 金 `(1.0,0.62,0.2)` の中点は `(0.64,0.59,0.6)` ＝ ほぼ無彩色になる。
実測でも FADE の遷移中（age 1.6）は発光画素の 99% が「白」に分類された。
加算合成の花火では白熱に見えなくもないので当面は許容しているが、
色相補間にするなら HSV か Oklab を通す必要がある。

**背景を足したぶん、上のスクリーン空間トレイルの弱点が目立つようになった。**
星は天球に貼り付いて正しく動くのに、花火の尾だけが画面に引きずられる。
比較対象ができてしまったので、以前より分かりやすく嘘に見える。解決策は同じ（instanced quad 化）。

**HDRI モードは素材を同梱していない。** ambientCG の Night Sky HDRI は CC0 だが
配布が EXR/HDR で、ブラウザが読めない。変換手順とスクリプトは
[sky/README.md](sky/README.md) と [sky/convert.py](sky/convert.py) にある。
置かなければ手続きの星空で動く。

**分裂は深さ1まで。** `shell → split` の2段で、`split.split` は持てない。
段数ぶん方向属性が必要になるうえ UI が指数的に複雑になる割に、
見た目は `shells[]` を重ねればほぼ代替できるため。深さ3以上はレシピ側で弾いている。
