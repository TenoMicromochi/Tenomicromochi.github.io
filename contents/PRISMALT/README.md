# WALLPAPER EDITOR — sample

`../SPEC.md` の要件に沿って組んだ動くサンプル。転換前の実装（`../index.html` /
`../style.css` / `../js/`）はそのまま残してあり、こちらは別ディレクトリの独立した実装。
共有しているのは数式だけの `cmf.js` / `colorspace.js` のコピーのみ。

## 動かす

ルートの `.claude/launch.json` の `wallpaper`（既定 port 8117 / 塞がっていれば空きポート）
→ `http://localhost:<port>/sample/`

**専用の開発サーバー `.claude/dev_server.py` を使う（素の http.server では動かない）。**
ALT 系の規約でこのツールの `style.css` は `@import url('/theme.css')` から始まるが、
Sandbox 配下で普通にサーバーを立てると `/theme.css` がこのフォルダを指して 404 になる。
かといって theme.css / alt.css をコピーすると本家と必ずドリフトする（Skill `alt-tool-new`
に、PALETALT と ANIMALT が実際にそれで token をずらした話がある）。
なので dev_server.py が `/theme.css` `/alt.css` `/fonts/` へのリクエストだけを
`SODENMIR/` へ付け替えている。SODENMIR へ統合したらこのサーバーは要らなくなる。

転換前（分光ラボ）を見たいときは同じ `wallpaper` エントリの `/` で。
（以前は `wallpaper-editor` / `wallpaper-sample` に分かれていたが、同じサーバーが
同じディレクトリを配っているだけだったので 2026-09-05 に1本へ統合した）

## 構成

```
sample/
├── index.html      画面（ALT系の3カラム）
├── style.css       @import 2行 + このツール固有の部品だけ
└── js/
    ├── cmf.js          CIE 1931 CMF（転換前からの純粋コピー）
    ├── colorspace.js   XYZ→sRGB / OKLab ガモットマップ（純粋コピー）
    ├── spectrum.js     光と素材の分光。2スペクトルのブレンドと積分・波長→色
    ├── band-editor.js  帯を直接編集するキャンバス部品（転換前からの純粋コピー）
    ├── presets.js      光の発光スペクトル / ブレンド両端に入れる色ガラス
    ├── scene.js        シーン状態（配置・field・光・ガラス・背景・カメラ）を1つに集約
    ├── shader.js       WebGL2 の自前レイトレ（ハイトマップ + 色つき影）と、
    │                   高さを焼くシェーダ・貼り付け用シェーダ
    ├── renderer.js     uniform 配線・色 LUT と高さの焼き込み・GPU時間の実測・
    │                   タイル描画（画面の描き直しと静止画の書き出し）
    ├── export.js       PNG（4096正方）と WebM（1回転ループ）の書き出し
    └── main.js         状態と DOM の配線、カメラ / 光の操作
```

## 画面（ALT系の共通フォーマット）

TEXTALT / GLYPHALT / ANIMALT / PALETALT と同じ骨格。`body.alt-app` + `.site-header` +
`.app-shell`、`style.css` は `@import url('/theme.css')` と `@import url('/alt.css')` で
始まり、色・ボタン・サイドバー・スライダーはツール内で再定義していない。

| カラム | 中身 |
|---|---|
| 左 | ARRANGEMENT / FIELDS / LIGHT / BACKGROUND / VIEW（操作ヒットもここ） |
| 中央 | レンダ + 書き出し範囲の枠 + info-chip |
| 右 | EMISSION / ABSORB A / ABSORB B のスペクトル、EXPORT STILL、EXPORT VIDEO |

`.app-shell` は alt.css だと「左カラム群 + 1fr」なので、右カラムぶんだけ
`grid-template-columns` を上書きしている。

**中央のキャンバスはドット絵ではない**（連続階調のレイトレ）ので、
`image-rendering: pixelated` も整数倍の制約も掛けていない。
ドット絵の不変条件が掛かるのは素材がドット絵のときだけ。

## 書き出し

| | PNG | WebM |
|---|---|---|
| 範囲 | 中央の正方形（枠の選択と無関係） | 選択中の枠 |
| 解像度 | 4096 x 4096 | 短辺 720（16:9 なら 1280x720） |
| 設定 | なし | `秒 / 1回転` のみ |

枠は `1:1 / 3:4 / 9:16 / 16:9`、中央固定・収まる最大サイズ（インセットなし）。
**インセットを付けないので 1:1 の枠が PNG の書き出し範囲と一致し、そのままプレビューになる。**
枠は動かさない（構図合わせは orbit / pan / dolly でやる）。

書き出し範囲は `uTanHalf` を `枠の高さ / ビューの高さ` 倍するだけで厳密に一致する。
`uv` が `uRes.y` で正規化されているので、縦の画角をその比率で縮めればよい。

### 動画は「オブジェクトが回る」

カメラ・背景・光は固定で、**ガラスだけ**が世界のZ軸まわりに1回転する（SPEC §7.3）。
カメラを周回させる案だと、一周のうち半分は背景面の裏へ回り込んで虚無が見えてしまう。
シェーダでは `toGlass()` の逆回転を `mapGlass` と3つのフィールドに掛け、
`mapBg`（背景）には掛けない。`mapGlass` が world 座標を受けて内部で回すので、
有限差分で取る法線は world のまま正しく出る。

1回転をフレーム数で割り切るので、ループは構造的に継ぎ目が無い。

**実装メモ: 収録ループに requestAnimationFrame を使わない。**
ウィンドウが前面に無い / 描画が止まっている間は rAF がスロットリングされて
収録が止まる（実際に踏んだ）。`setTimeout` なら裏でも進み、60fps の頭打ちも無い。
`captureStream(0)` の `0` は手動フレーム送りの指定で、これが無いと実時間記録になり、
1フレームのレイトレに時間が掛かるぶんコマ落ちしたスローモーションになる。
実測 1280x720 で 42ms/frame（8秒=240フレームなら 10秒ほど）。

## 軸とパターン（SPEC §4.1.1）

各フィールドは **x / y / z のチェックボックス**で軸を選び、複数ONのときの合成を
**8つのパターンタブ**から選ぶ。パターンは 基準 x 合成 の直交表（id = 基準*4 + 合成）。

| id | 名前 | 基準 | 合成 | 出る形（x+y） |
|---|---|---|---|---|
| 0 | diagonal | 端から | mean | 対角の坂 |
| 1 | ridge | 端から | max | L字の尾根 |
| 2 | valley | 端から | min | L字の谷 |
| 3 | corner | 端から | dist | 角からの1/4円 |
| 4 | diamond | 中央から | mean | 斜め45度の四角錐 |
| 5 | pyramid | 中央から | max | 四角錐 |
| 6 | cross | 中央から | min | 十字の尾根 |
| 7 | dome | 中央から | dist | ドーム |

- 軸ゼロ = `const`（`lo` の値）。軸1本だと合成が効かず ramp / fold の2択に縮退する
  （UIのヒント行がそう出る）
- 中央基準は最後に `1-` で反転して山にしてある。`dome` + `invert` が
  転換前の `radial`（中心が低いお椀）と一致する
- height だけは z を出さない（列の高さは z に依らないため）

## 格子と use grid z

`grid x / y / z` はセルの個数。`use grid z` を ON にすると高さが `grid.z` 段に
スナップし、セルが立方体になる。**このとき `max height` は使われない**（グレーアウト表示）。
3x4x7 のような配置ができる。高さフィールドの `lo/hi` はどちらのモードでも割合のまま。

`refit camera to grid` は格子の実寸からカメラ距離を出し直す。20x2 のような
細長い格子でも画面に収まる。

隙間は **`gap x/y` と `gap z` で別々**に持つ。`gap z` は `use grid z` のときだけ効く
（連続高さには割る段が無いため。OFF のときはグレーアウトする）。

| gap x/y | gap z | 出るもの |
|---|---|---|
| 0 | 0 | 中身の詰まった1つの塊 |
| >0 | 0 | 柱の群れ（縦は融合したまま） |
| 0 | >0 | 板が積み重なったもの |
| >0 | >0 | **独立したキューブが格子状に並ぶ**（3x3x3 なら27個） |

`gap z` の既定は 0 なので、何もしなければ従来どおり「縦は融合した柱」になる。

**占有はハイトマップのまま**であることに注意。`gap z` は積んだセルの間隔を空けるだけで、
オーバーハングや空洞が作れるようになったわけではない（SPEC §5.1）。

### 実装メモ: 段を全部ループしない

`sdColumn` は段の数だけループしたくなるが、それをやると 3x3 近傍 x 段数 になって
レイマーチが一気に重くなる。**`p.z` が入っている段だけ**を見れば足りる
（同じ列のセルは x/y の広がりが同じなので、いちばん近いセルは z だけで決まる）。
1個評価すれば厳密に正しく、コストは段の無いときと同じ。

z 方向も x/y と同じく、`gap z = 0` のときは `MERGE_OVERLAP` ぶん実際に重ねている。
接するだけだと段の境目で SDF が 0 になって偽の界面ができるため。

## ビューの操作（左カラム VIEW にも出してある）

| 操作 | 動き |
|---|---|
| 左ドラッグ | カメラの周回（az / el） |
| **ホイールクリック長押し + ドラッグ** | **平行移動**（注視点をカメラの right/up 平面上で動かす） |
| ホイール | ドリー（寄る / 引く） |
| 右ドラッグ | 光の向き（SPEC §8） |
| ダブルクリック | 視点リセット（格子に合わせて再フィット） |

平行移動は 1px の移動量をその距離での world 幅に合わせてあるので、
ズーム倍率を変えても掴んだ感触が変わらない。

## スペクトラムエディタ

画面下段に横3枚。**発光スペクトル（光・シーンで1つに固定）／吸収スペクトル A ／ B**。
部品は転換前の `js/band-editor.js` をそのままコピーして使っている。

空きをクリックで山を追加（各8本まで）、左ドラッグで移動、右ドラッグかホイールで Q、
ダブルクリックで削除。山を動かすたびに (d, t) の2次元 LUT が焼き直される。
ヘッダの色チップは、光はその光そのものの色、ガラスは等エネルギー白で見たその色。

**デザインは未着手。** SPEC §9 で保留にしてある画面レイアウトの検討はこれから。
まず使える形で下段にねじ込んである。

## SPEC のどこを満たしているか

| SPEC | このサンプルでの実装 |
|---|---|
| §2 カメラ自由回転 | 透視投影。左ドラッグで周回、ホイールでドリー、ダブルクリックで初期視点 |
| §3–4 軸→フィールド | `height` / `density` / `ior` / `mix` の4つを**同じ1つの仕組み**で回す。x/y/z を複数ONにでき、合成は8パターン。lo/hi は自由。invert つき |
| §4.1 スペクトラムエディタ | 発光 / 吸収A / 吸収B の3枚を下段に。帯を動かすと LUT が焼き直される |
| §5.1 格子 x/y/z | セルの個数で持つ。`use grid z` ON で高さが段にスナップし、`max height` は無視される |
| §4.1 連続フィールド | ピース単位ではなく、当たった点・経路上の点でその都度サンプル。大きい柱にも小さい柱を並べたのと同じ勾配が乗る |
| §4.2 IOR | ガラスに入った点で1回だけ引き、その塊を抜けるまで使い回す |
| §4.3 スペクトル中間値 | `A_mix(λ,t) = (1-t)·A_A + t·A_B`。色は **(光路長 d, 混合率 t) の2次元 LUT** を1回引くだけ |
| §5 ハイトマップ占有 | 格子の列ごとに高さフィールドで占有を決める。穴・オーバーハングなし |
| §5.2 隣接マージ | `gap = 0` で隣接列が継ぎ目なく融合（地形・板の集合）。`gap > 0` で離れて別々の柱（散らばった柱） |
| §6 バックライト / void色 | バックライトは常に光の色で固定（黒にできない）。void色は独立した普通の sRGB、スペクトルでは計算しない |
| §7 書き出し | 静止画のみ。編集中の構図（カメラ・配置・色・光）を、指定した幅で**シーンごと再レンダリング**して PNG 保存 |
| §8 地面・影・光の位置 | 光に向きを持たせ（右ドラッグ）、背景面に影を落とす。**影は色つき**（光源へ向かうシャドウレイに同じ Beer-Lambert を使い回す）。背景とガラスの距離を持つ |
| §8.1 背景プリセット | off / floor / wall / floor&wall / cyclorama をタブで切り替え。床・壁の色は void色に連動 |
| §2 Undo/Redo なし | 実装していない |

## 既定のシーン

昼光 6500K（黒体）、ルビー→コバルトの横グラデーション、手前が低く奥が高い 6x6 の柱、
床の上、手前右上からの光。柱の背後に色つきの影が落ちる。
`use grid z` は既定 OFF なので、高さは連続のまま。

## 軽量化（2026-09-04）

計測は GPU タイマー（`EXT_disjoint_timer_query_webgl2`）で取った実測。
RTX 3060 / 694x646 / 既定シーン。

### 何が重かったか

歩数を数えるシェーダを仕込んで測ると、`traceScene` が **平均57歩/画素**。
1歩ごとに `mapGlass` が 3x3 の列を回して `heightAt` を呼ぶので、
**1画素あたり500回以上**も高さフィールドを評価していた。ここが支配項だった。
（`traceInside` 13歩、`traceShadow` 7歩。影は全体の2割弱）

### やったこと1: シェーダの内側（出力は変えずに 33〜47% 減）

1. **`mapGlass` の 3x3 ループに、高さに依らない下界で足切りを入れた。**
   列の箱までの水平距離は SDF の下界なので、それが今のベストに届かない列は
   `heightAt` を呼ばずに飛ばせる。9列の評価が実質2〜3列になる
2. **`heightAt` を格子テクスチャから引くようにした。** 高さは列ごとの定数なのに
   レイマーチの毎歩で計算し直していた。`BAKE_FS` が grid.x x grid.y の小さな
   テクスチャに焼き、レンダ側は `texelFetch` 1回で済ませる
3. シャドウレイを、マーチ前にグリッドのAABBで判定して外れていれば丸ごと省く

| 格子 | 前 | 後 |
|---|---|---|
| 6x6（既定） | 13.91 ms | 9.22 ms |
| 6x6 dome | 13.88 | 9.03 |
| 6x6x8 use grid z | 21.86 | 13.58 |
| 12x12 | 33.67 | 18.86 |
| 20x20 | 46.49 | 24.36 |

**出力は変わっていない。** 8つのパターン・invert・軸ゼロ・use grid z・gap z・
非正方の格子・背景4種を総当たりで、旧実装と画素単位で突き合わせて確認した。
残る差はシルエットの際の数十画素だけで、これは旧実装の高さを 1e-7 動かしたときに
出る差より小さい（＝このレイトレーサ自身が持っている際の揺れの範囲）。

**踏んだ落とし穴:** 高さを 24bit に詰めるとき、`r = 1.0` で `16777215.5` になるが
float32 は 24bit しか持たないのでこれが `16777216` に丸め上がり、4バイト目へ溢れて
上3バイトが 0 になる。**段にスナップすると r がちょうど 1.0 になるので普通に踏む**
（いちばん高い柱が高さ0で焼かれた）。`min(..., 16777215u)` で頭打ちにして塞いだ。

### やったこと2: 表示の出し方

レイトレを画面に直接描かず、いったんオフスクリーンのテクスチャに描いてから貼るようにした。
これで **低解像度の下描きを消さずに、高解像度でタイルごとに描き直せる**。

- 操作中は解像度を落として即出し、手が止まったら（140ms）タイルに割って描き直す。
  1回のドローが短いままなので、非力な GPU でも「離した瞬間に固まる」ことがない
- **落とす倍率は固定値をやめた。** 前は 0.6 決め打ちだったが、公開先の GPU は分からない。
  実測した「100万画素あたりの GPU 時間」から必要な倍率を逆算する。
  一気に描いても 40ms 以下で終わる見込みなら、下描きを挟まずそのまま本描画する
- **info-chip の `ms` が本物になった。** 前は `drawArrays` を投げるまでの CPU 時間で、
  GPU の仕事量とまったく関係が無かった（実測17msのところを8.3msと表示していた）

低解像度のパスから割り出す速さの見積もりは、やや重め（安全側）に出る。
画素数が少ないと GPU が遊ぶぶん1画素あたりが割高になるため。
本描画が一度走れば正しい値に寄るので、そのままにしてある。

### やったこと3: 書き出しの事故防止

**PNG が 4096x4096 を1回のドローで描いていた。** 3060 で 398ms。1/10 の性能の GPU なら
約4秒かかり、**Windows の TDR（既定2秒）でドライバがリセットされて WebGL の
コンテキストごと落ちる。** 512x512 のタイル64枚に割った。

| | 前 | 後 |
|---|---|---|
| 4096x4096 | 単発ドロー 398ms | 合計 622ms / **1回のドローは最長 43ms** |

合計時間は増えるが（タイルごとの同期と2D キャンバスへの組み立てぶん）、
1回のドローが短いので事故が起きない。進捗もボタンに出る。
組み立て先は 2D キャンバスなので、表示用キャンバスを 4096 にリサイズすることも無くなった。

**実装メモ: タイルの合間に `setTimeout(0)` を使わない。** 入れ子だと 4ms に丸められ、
さらに**タブが裏に回ると 1秒まで延ばされる**（64タイルなら1分以上）。
`requestAnimationFrame` は裏で止まるのでもっと悪い。`MessageChannel` はどちらの制限も
受けないので、これで制御を返している（`renderer.yieldToBrowser`）。
動画の収録ループも同じものに乗せ替えた。

**実装メモ: タイル描画中はライブ描画を止める。** タイルごとにブラウザへ制御を返すので、
その隙間にライブ描画が割り込むと描き先のテクスチャを別のサイズに作り直され、
途中まで描いた絵が壊れる（実際に壊れた）。書き出しと収録の間は `lockRender` で止め、
画面の描き直しのほうは世代番号で「新しいのが来たら古いのが降りる」形にしてある。

### 手を出していないもの

- **ハイトフィールドの DDA 化**（列を順に辿る厳密な交差判定）。5〜10倍は見込めるが、
  面取りと `gap = 0` の融合が SDF 前提なので、直した不具合を踏み直す大手術になる
- **`segs` や反復回数の削減。** 速くはなるが画が変わるので、軽量化ではなく
  品質設定として別に扱うべきもの

## 直した不具合（初版の動作確認で見つけたもの）

- **融合した塊（`gap = 0`）に白い画素ノイズが乗っていた。** 原因は
  「内部の全反射が暴れる」ことではなく、**閉じ込められたまま打ち切った光に
  素通しの光を足していた**こと。抜けられた隣の画素との差が明るい斑点になる。
  転換前の `js/gl3d.js` が同じ落とし穴を踏んで `tint = vec3(0.0)` で直しており
  （README の「実装上の落とし穴」）、サンプルはそれを取りこぼしていた。
  吸収体の中の光は最終的に消えるので 0 が正しい。内部反射の追跡も 4 → 6 回に増やした。
  **副作用として、融合した大きな塊は以前より暗く出る**（これが物理的に正しい側）
- **`gap = 0` でも列同士が重なっていなかった。** SDF の `+ uBevel … - uBevel` は
  打ち消し合うので外形は `halfXY` ちょうどのままで、共有面で `mapGlass` が 0 になり
  塊の内部に偽の界面ができていた。`MERGE_OVERLAP` で実際に重ねるようにした
- **背景 `off` にするとガラスが消えていた。** 近傍3x3が空のとき `mapGlass` が `1e9` を
  返すため、背景も無い（`mapBg` も `1e9`）と歩幅を抑えるものが無くなり、光線が
  最初の1歩でシーンごと飛び越していた。床・壁があるときだけ動いていたのは
  背景面が歩幅を抑えていたから。グリッド全体のバウンディングボックスまでの距離を
  返す `gridBound()` を足して解決

## 既知の粗さ（詰めは別途）

- 面取りキューブの角で稀に緑の点が出る（SDF 法線の縮退。転換前 gl3d.js と同じ現象）
- カメラを背景面の裏へ回すと、その面は虚無（バックライト）になる。SPEC §8.1 の許容範囲
- 高さフィールドに `z` 軸を割り当てても意味がない（列の高さは z に依らない）ため
  UI では height に z を出していない
- スペクトラムエディタの見た目は未調整（数値欄が折り返す等）。SPEC §9 のとおり
  レイアウトの検討はこれから
